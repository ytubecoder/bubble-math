# Bubble Math

Single-file kids' math toy (`index.html` — no deps, no build) for a 3-year-old who reads numerals. Canvas bubbles carry values 1–50; merging adds, tearing/splitting subtracts. Everything is deliberately slow and abortable (~1.1s blend, ~0.7s tear) so a small child can change his mind mid-gesture.

## Design invariants

- **Sum conservation.** Every interaction — merge, tear, double-tap, two-finger split, finale burst — conserves total value. Only the + button and the 25s trickle add value. A change that breaks this is wrong.
- **Additive interactions only.** The kid has already learned drop-to-merge, double-tap split, and the two-finger split. New physics (momentum bonding, one-finger tear, the overcrowding reset) are layered on top; never remove the old paths.
- **Size layering.** Draw order is biggest-at-back / smallest-on-top, and `hitTest` returns the smallest bubble under the finger — so small fingers grab the small bubble sitting on a big one. Keep draw order and hit order in sync. **Exception: the actively-dragged bubble always draws on top**, regardless of size — otherwise carrying a big bubble near/over a smaller stationary one makes it visually vanish underneath, which reads as a bug even though it's the "smallest wins" rule working as designed.
- **Merging on release requires real center alignment, not loose proximity.** `MERGE_ALIGN_RATIO` (0.34× combined radii) gates `attemptDropMerge` — releasing a bubble merely nearby another no longer joins them; centers have to be genuinely brought together. The same predicate (`findMergeCandidate`) drives a live "release here to join" glow while still dragging, so what merges on release is never a surprise — it was already visible before the finger lifted. In practice momentum bonding (see below) preempts most real drags before they'd ever reach this tight a distance, since bonding's own proximity gate (`BOND_START_RATIO`, 1.05×) is looser and triggers first — this path mainly matters for a slow, deliberate final placement that never crossed the bond speed threshold. **This threshold is only reachable because of a matching repulsion exemption**: the soft mutual-repulsion pass (section 5 of `update()`) otherwise re-separates any two non-bonded overlapping bubbles back to exactly touching distance every frame, which sits well outside 0.34× — a dragged bubble and its nearest neighbor within `BOND_START_RATIO` are exempted from that repulsion (same idea as the existing bonded-pair exemption) specifically so a slow deliberate push can actually converge past "touching." Don't tighten `MERGE_ALIGN_RATIO` or touch that exemption without re-testing reachability via a real (non-teleported) slow drag — it's easy to silently regress back to an unreachable threshold. The glow ring (`drawMergeReady`) is drawn *after* the bubble layer for the same reason the z-order exception exists: a bigger dragged bubble sitting on top of a smaller candidate would otherwise paint over its own glow ring.
- **Grab position decides the split proportion, not pull distance.** One-finger tear, two-finger split, and double-tap all use the same geometry (`circleSplitFraction`): grab/tap near the bubble's center → close to 50/50; near the rim → a thin sliver. The amount is locked in at grab time (`tearBudValue`) and pulling further never changes it — only whether/when it commits.
- **Anchor-and-hold, not spring elastic, decides when a one-finger drag tears.** The body follows the finger with a plain spring while dragging (`followRate`) — feels attached, used for carrying a bubble to another one for a merge. Whether that counts as a tear is decided by two speed-independent things: the finger has travelled past `SPLIT_TRIGGER_RATIO*r` from where it first touched down, and it has now genuinely stopped (`settled`, debounced via `SETTLE_DWELL` so one noisy frame can't misread a fast carry as a stop). Once anchored the body freezes in place — no spring left to drift it back together — until the finger returns within `SPLIT_RELEASE_RATIO*r` of touchdown. This works at any drag speed on purpose (a hard speed cap was tried earlier and rejected for the opposite reason: it never converges on a long drag, so every fast carry misreads as a pull-apart) — a prior version used `TEAR_STICKINESS` to fake this off of live gap-to-finger, which had a hard mathematical ceiling that a slow sustained pull could never cross; don't reintroduce that.
- **Bond immunity on finale spawns.** Finale pieces get `bondCooldown: 2.5` — without it the burst pieces momentum-bond back together within a second (10+10=20 happened spontaneously) and the finale can loop.
- **One story at a time.** Drag/tear effects are suppressed while the dragged bubble is in a bond (otherwise "4 + 6" and "4 − 2" render simultaneously).
- **Overcrowding reset is a deliberate sum-conservation exception.** Past `MAX_BUBBLES` (16), `chaos` kicks every bubble with a random velocity, bounces them for `CHAOS_BOUNCE_TIME` (drags/bonds/ghost-fill suppressed meanwhile), then pops everything and calls `spawnInitial()` — a fresh start, not a merge. This is the one place total value is allowed to reset; it's the antidote to mashing the + button until the mat is full.

## Testing gotchas (all hit for real, 2026-08-01)

- Playwright MCP screenshot round-trips are slower than the game's animations — merge→finale→burst completes between tool calls. Capture mid-animation frames from *inside* the page: return `canvas.toDataURL('image/png')` from `browser_evaluate` (use `filename` param), then base64-decode.
- Synthetic PointerEvents are untrusted: `setPointerCapture` throws on them (already try/catch-wrapped in the code). Drive the game by dispatching PointerEvents on the canvas via evaluate.
- The pinned Playwright profile persists `localStorage` across sessions: `bubblemath.target` / `bubblemath.muted` from an old test can silently disable features (a "broken" ghost socket was just the target toggled off weeks-old-state). Check localStorage before diagnosing.

## Testing gotchas (2026-08-03, verifying the tear redesign)

- The game state lives in a closure (`(() => {...})()`), invisible from `browser_evaluate` by default. To inspect `bubbles`/`chaos`/etc. live, temporarily add `window.__debug = { get bubbles(){return bubbles;}, ... }` right before the boot section, test, then **remove it before finishing** — don't ship it.
- A single frame's computed finger velocity (`dist(fingerX,prevFingerX)/dt`) is noisy: browser event delivery isn't perfectly even, so one lucky quiet frame during an otherwise-continuous fast drag can read as "stopped." Any speed-based gesture check needs a short dwell (accumulate time below the threshold, only trust it past ~0.1s) or a real fast carry will occasionally misfire as a stop.
- Synthetic `pointermove` dispatched slower than the game's ~60fps update loop (e.g. one event per 40-60ms) leaves several update() frames per event where `fingerX` hasn't changed — those frames read as zero velocity even mid-"fast" drag. When testing anything speed-sensitive, dispatch at ≤16ms intervals to approximate real touch sampling, or the test itself manufactures false "stops."
- When a value that should be converging toward a target isn't moving, check whether the object you're still polling by id already turned into the *remainder* of a split/merge (same id, new value, recoiling under normal drift) rather than assuming the mechanic is stuck — trace intermediate decision variables (not just final position) before concluding there's a bug.

## Testing gotchas (2026-08-03, verifying drag z-order + merge alignment)

- Testing release-triggered behavior (`attemptDropMerge`, etc.) by dispatching `pointerdown` then directly mutating a live bubble's `x`/`y` (via the `window.__debug` object reference) and jumping straight to `pointerup`, skipping any `pointermove`: the release handler checks `b.dragMoved` to decide tap-vs-drop, and that flag is only set inside the `pointermove` listener — skip it and every release is misread as a tap, silently taking the wrong code path. Either dispatch a real `pointermove` first or also set `mover.dragMoved = true` directly.
- Momentum bonding preempts almost every realistic drag approach, even a deliberately slow one: closing speed is computed from actual bubble velocity (spring-follow + the target's own ambient wander), not raw finger speed, so even a ~35px/s creep crossed `MOMENTUM_THRESHOLD` and triggered an automatic bond-and-merge before reaching a tighter test distance in every trial tried. To test position-based logic (like a merge-distance ratio) in isolation, teleport the bubble's `x`/`y` directly and release in the same synchronous call, with **zero** intervening animation frames — one awaited frame is enough for the physics tick (spring-follow, and especially the soft mutual-repulsion pass, which reacts hard to a suddenly-huge overlap from a teleport) to move the bubble again and invalidate the position you just set.
